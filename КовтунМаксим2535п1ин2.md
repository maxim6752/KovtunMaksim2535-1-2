# Практика 10. Инцидент «Чёрной пятницы»: серверная валидация данных

**Роль:** Lead-аналитик команды, разрабатывающей корпоративную систему бронирования ресурсов.

**Корневая причина инцидента:** клиентская валидация (формы, HTML5) считалась единственным барьером. Клиент находится вне доверенной зоны: любой запрос можно отправить напрямую через Postman/cURL. Сервер должен считать все входящие данные недоверенными и проверять их самостоятельно.

---

## 1. Матрица требований к серверной валидации

| № | Описание инцидента | Тип требуемой серверной проверки | Конкретное правило |
|---|---|---|---|
| 1 | Бронь переговорной с датой начала 2026-12-01 и датой окончания 2026-11-01 | **Бизнес-логика** (основная); дополнительно **Тип данных / Формат** | `end_date > start_date` (строго); `start_date >= now()` (нельзя бронировать в прошлом); обе даты парсятся как ISO 8601, иначе `400`; максимальная длительность брони (например, `end_date - start_date <= 8 ч`); отсутствие пересечения с существующими бронями ресурса |
| 2а | Заявка на выдачу **−50** ноутбуков | **Диапазон / Формат**; **Бизнес-логика** | `quantity` — целое число (integer), не float и не строка; `1 <= quantity <= MAX_PER_REQUEST` (например, 5); `quantity <= доступный остаток на складе` |
| 2б | Пользователь с возрастом **−5** лет | **Диапазон / Формат**; **Тип данных** | `age` — integer; `18 <= age <= 100`. Лучше не принимать возраст от клиента вовсе, а хранить дату рождения (`birth_date <= today`, `birth_date >= today - 100 лет`) или брать данные из корпоративного профиля сотрудника |
| 3 | Пользователь сам присвоил себе роль `super_admin` в JSON-запросе | **Авторизация / Роли** (атака Mass Assignment / Privilege Escalation) | Поле `role` игнорируется во входном DTO (whitelist разрешённых полей); роль берётся только из серверного источника (БД/токен), а не из тела запроса; изменение роли доступно только пользователю с правом `users:manage_roles`, и назначить роль выше своей нельзя (`new_role.level <= actor.role.level`); все смены ролей пишутся в audit-лог |
| 4 | В поле «Комментарий» передан `<script>…document.cookie…</script>` (Stored XSS) | **Безопасность / Санитизация** | Сервер: ограничение длины (например, `<= 1000` символов), удаление/запрет HTML-тегов (`strip`/allowlist, например, через библиотеку санитизации). Вывод: контекстное экранирование (HTML-escape) при рендере в дашборде. Дополнительно: заголовок `Content-Security-Policy` (запрет inline-скриптов), cookie с флагами `HttpOnly; Secure; SameSite` |

**Сквозные требования ко всем эндпоинтам**

- Валидация по схеме (JSON Schema / DTO) с запретом лишних полей (`additionalProperties: false`).
- Единый формат ошибок: `400` (невалидный формат) / `403` (нет прав) / `409` (конфликт бизнес-правил) / `422` (семантическая ошибка).
- Ограничение размера тела запроса и rate limiting.
- Правило «валидируем на сервере всегда; клиент — только для удобства пользователя».

## 3. Архитектурное решение методом взвешенной суммы (WSM)

### 3.1. Альтернативы

- **A1. API Gateway** — валидация на уровне шлюза (схема запроса, размеры, отсечение мусора до микросервисов).
- **A2. Application Layer** — валидация внутри микросервиса бронирования (DTO, доменные правила).
- **A3. Database Constraints** — только ограничения СУБД (`NOT NULL`, `CHECK`, `FK`, `UNIQUE`).

### 3.2. Критерии и веса (сумма = 1,0)

| Критерий | Вес Wj | Обоснование |
|---|---|---|
| Надёжность (защита при прямом доступе к БД) | **0,35** | Именно из-за обхода защитных слоёв случился инцидент. Некорректные данные в БД — самый дорогой вид ущерба |
| Гибкость изменения правил | **0,25** | Бизнес-правила (лимиты, сроки броней) меняются часто; нужно менять их без миграций БД и пересборки шлюза |
| TCO (поддержка и обучение) | **0,25** | Команда должна уметь поддерживать решение; бизнес-логика на языке разработки проще для тестирования и отладки |
| Производительность | **0,15** | Валидация проверок формата и диапазонов занимает миллисекунды, поэтому для корпоративной системы бронирования это не узкое место |
| **Итого** | **1,00** | |

### 3.3. Оценки Xij (шкала 1–10, где 10 — лучше всего)

| Критерий (вес) | A1. API Gateway | A2. Application Layer | A3. DB Constraints |
|---|---|---|---|
| Производительность (0,15) | 9 — отсекает мусор до сервисов | 7 | 8 — быстрые проверки, но отказ приходит поздно, после запроса к БД |
| Гибкость (0,25) | 6 — правила в конфиге шлюза, но сложные/доменные не выразить | 9 — любой код, быстрый деплой, юнит-тесты | 3 — изменение через миграции схемы |
| TCO (0,25) | 5 — отдельная технология и дублирование правил | 8 — привычный стек команды | 6 — просто для простых правил, сложно для бизнес-логики |
| Надёжность (0,35) | 3 — прямой доступ к БД или сервису в обход шлюза не защищён | 6 — защищает только если ходят через сервис | 10 — защита работает при любом способе доступа |

### 3.4. Расчёт: Si = Σ(Wj · Xij)

**A1. API Gateway**
S1 = 0,15·9 + 0,25·6 + 0,25·5 + 0,35·3
S1 = 1,35 + 1,50 + 1,25 + 1,05 = **5,15**

**A2. Application Layer**
S2 = 0,15·7 + 0,25·9 + 0,25·8 + 0,35·6
S2 = 1,05 + 2,25 + 2,00 + 2,10 = **7,40**

**A3. Database Constraints**
S3 = 0,15·8 + 0,25·3 + 0,25·6 + 0,35·10
S3 = 1,20 + 0,75 + 1,50 + 3,50 = **6,95**

| Альтернатива | Итоговый балл Si | Место |
|---|---|---|
| A2. Application Layer | **7,40** | 1 |
| A3. Database Constraints | 6,95 | 2 |
| A1. API Gateway | 5,15 | 3 |

### 3.5. Вывод

Ни один подход в одиночку не закрывает все риски, поэтому оптимальна **комбинация по принципу эшелонированной защиты (defense in depth)**:

1. **Application Layer — основной слой** (лидер по WSM, 7,40). Здесь находятся все бизнес-правила (`end_date > start_date`, остаток на складе, проверка ролей, санитизация). Правила гибко меняются и покрываются юнит-тестами.
2. **Database Constraints — последняя линия обороны** (6,95). Самые критичные инварианты (`CHECK (quantity > 0)`, `CHECK (end_date > start_date)`, `NOT NULL`, `FK`) дублируются в БД: они защищают данные даже при баге в сервисе или прямом доступе к БД.
3. **API Gateway — лёгкий предохранитель** (5,15). Только грубая фильтрация: ограничение размера тела, проверка Content-Type, базовая JSON-схема, rate limiting. Доменную логику здесь не держим, чтобы не дублировать правила и не усложнять поддержку.

**Анализ чувствительности:** разрыв между A2 и A3 невелик (0,45). Если бы вес «Надёжности» вырос примерно до 0,5 при пропорциональном снижении остальных, A3 вышел бы вперёд. Это подтверждает, что ограничения БД обязательны, но одних их недостаточно: они не умеют выразить сложные правила, не дают понятных сообщений об ошибках и не умеют санитизировать HTML.

## 4. Обновлённый Definition of Done (DoD)

К существующим пунктам DoD добавить:

1. **Автоматизированные негативные тесты в CI.** Для каждого нового или изменённого API-эндпоинта в пайплайне CI есть автотесты, проверяющие отклонение заведомо некорректных данных: отрицательные и нулевые количества, `end_date <= start_date`, лишнее поле `role` в теле запроса, `<script>` в текстовых полях, запрос без нужных прав. Пайплайн блокирует мерж, если эти тесты отсутствуют или падают; дополнительно в CI включены SAST-проверка (поиск XSS и Mass Assignment) и проверка миграций на наличие `CHECK`/`NOT NULL` для критичных инвариантов.
2. **Обязательное ревью по чек-листу.** Pull Request с новым или изменённым эндпоинтом не может быть смёржен без одобрения минимум одного рецензента, который заполнил чек-лист из раздела 2 (все пункты «Да» или «Неприменимо» с пояснением); это условие настроено как branch protection rule в репозитории и не может быть обойдено ручным мержем.

*Примечание: числовые оценки в WSM — экспертные; при желании их можно скорректировать под контекст проекта, а вывод проверить анализом чувствительности (см. п. 3.5).*
